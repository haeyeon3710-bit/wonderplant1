# 블로그 CMS 사용과 운영 전환

## 현재 검증 환경

GitHub의 `feat/supabase-cms` 브랜치와 PR #1의 Netlify Deploy Preview에서 CMS를 검증한 뒤, 사용자의 요청으로 main에도 적용합니다. 기본 Netlify 주소를 아직 정식 발행 전 개발 사이트로 사용하므로, 기본 배포와 Deploy Preview는 같은 preview 글과 통계를 사용합니다. 관리자 계정과 카테고리도 그대로 유지합니다. 서버의 `CMS_ENVIRONMENT` 값으로 preview/production을 구분하는 DB 구조는 유지하며, 실제 운영 전환 때 필요한 글만 이전하고 운영 통계는 새로 시작합니다.

관리자 경로는 `/adm`, 로그인은 `/login`, 작성은 `/adm/new`, 수정은 `/adm/edit?id=...`입니다. 공개 글은 `/blog/한글-슬러그`에서 열립니다. 목록은 기본 전체보기이며 카테고리·최근 발행순·누적/최근 7일/최근 30일 조회순을 제공합니다.

## 글 작성과 복구

1. `/login`에서 본인이 설정한 비밀번호와 관리자 아이디로 로그인합니다.
2. ‘새 글 쓰기’에서 제목, 한글 슬러그, 카테고리, 카드 설명과 이미지/글 블록을 작성합니다. 카드 설명은 공백 포함 최대 130자이며 최소 글자 수 제한은 없습니다. 빈 설명도 저장·발행할 수 있습니다.
3. ‘저장’은 선택한 게시 상태를 유지합니다. 새 글은 임시저장으로 시작하며, ‘즉시 발행’을 누르면 최초 발행일시를 DB에서 기록합니다. 발행 뒤 수정하거나 비공개로 바꿔도 최초 발행일시는 유지됩니다. 공개 본문은 한국 시간 기준 최초 발행일시를 ‘발행일 :’로 표시하며 수정일시는 관리자/검색 메타데이터에 보존합니다.
4. ‘미리보기’는 카드와 본문을 구분합니다. 설명글은 카드와 검색 메타데이터에만 들어갑니다. 이미지 파일은 PNG/JPEG/WebP/GIF, 파일당 20MB입니다.
5. ‘사본’과 JSON 가져오기는 새 ID·새 주소의 초안을 만듭니다. 기존 DB 글과 브라우저 저장 데이터를 덮어쓰지 않습니다. DB JSON의 원본 HTML도 정화 후 보존합니다.
6. 삭제 전 JSON을 자동 다운로드합니다. 복구할 때는 ‘JSON 초안 가져오기’를 사용하고, 카테고리와 슬러그를 확인한 뒤 발행합니다. 이미지 파일은 글 삭제 후에도 비공개 저장소에 보존됩니다. 삭제된 글의 조회 기록은 함께 제거되며, 새 초안의 조회수는 0부터 시작합니다.

대표 이미지의 카드 표시와 카드 미리보기는 3:2 가로 비율입니다. 원본을 변경하지 않고 중앙 기준으로 맞추므로 비율이 다른 원본의 가장자리는 일부 잘릴 수 있습니다. 이미지 설명은 HTML 이미지의 `alt` 대체 텍스트로 쓰입니다. 별도 문장으로 노출되지 않으며 이미지 검색과 화면 읽기 도구에서 사용합니다. 본문에서 보이는 설명은 이미지 블록의 선택 ‘캡션’입니다. 메인 RECENT는 DB에서 최초 발행일시 최신순으로 최대 3건을 자동 표시합니다.

## 예약 발행

게시 상태에서 ‘예약 발행’을 선택하고 날짜와 시간을 **한국 시간(Asia/Seoul)** 기준으로 선택한 뒤 ‘예약 발행’ 또는 ‘저장’을 누릅니다. 시간대가 다른 브라우저에서도 입력값은 한국 시간으로 처리합니다. 대표 이미지·대체 텍스트·본문이 필요하고, 설명글은 최대 130자만 제한합니다.

예약 중에는 일반 방문자의 목록·상세·이미지·사이트맵에 노출되지 않습니다. 관리자 목록의 ‘예약 발행’ 필터와 예약 시각으로 확인할 수 있습니다. 수정 폼에서 시각을 변경하거나 임시저장/비공개로 저장하면 예약을 취소할 수 있습니다. 사본과 JSON 가져오기는 예약이 해제된 새 초안으로 생성됩니다.

Supabase `pg_cron`의 `cms-publish-scheduled` 작업이 매분 DB 함수를 실행합니다. 브라우저가 닫혀도 작동하며 Netlify 재배포는 필요하지 않습니다. 지정 시각 이후 다음 실행에서 공개되므로 정상 동작 시 최대 약 1분 차이가 있습니다. 처음 실제 공개된 시점을 `published_at`에 기록합니다. 이미 발행했던 글을 다시 예약하면 기존 최초 발행일시를 보존합니다. 예약 분류가 비활성이면 발행을 보류하고 다시 활성화한 후 처리합니다. DB가 일시 정지되거나 작업이 실패하면 복구 후 다음 실행에서 처리되므로 실제 발행일시는 그때가 됩니다.

함수는 외부 API로 노출하지 않고 DB 소유자 작업만 실행할 수 있습니다. 한 번에 최대 100건을 잠금으로 처리하며 동시 실행 시 중복 발행을 방지합니다. Cron 실행 로그는 위 두 CMS 작업에 한해 매일 7일 이전 기록을 정리합니다. Supabase Integrations → Cron에서 실행 상태를 확인합니다. preview/production 게시글의 환경 값은 바꾸지 않습니다.

이전 브라우저 초안은 **작성했던 주소와 브라우저**의 localStorage에 남습니다. 다른 Netlify 주소에서는 같은 저장소에 접근할 수 없으므로, 원래 화면의 JSON 내보내기 후 현재 관리자 화면으로 가져옵니다. `wonderful-admin-demo-v1`은 새 코드에서 삭제·수정하지 않습니다. 작성 중 복구본은 사용자별 별도 키에 저장합니다. 동시에 열린 두 화면의 수정 충돌은 버전 검사로 거절하고 복구본을 보존합니다.

## 이미지와 공개 페이지 최적화

새 PNG/JPG/WebP 업로드는 브라우저에서 긴 변 1,600px 이하·품질 84의 WebP로 변환합니다. 원본 파일 선택 한도는 20MB로 유지합니다. 사용자 PC의 원본은 변경하지 않습니다. GIF와 움직이는 WebP는 비공개 저장소에 원본을 먼저 보관한 뒤 관리자 인증을 거친 서버에서 WebP로 변환하며 프레임별 표시 시간과 반복 횟수를 보존합니다. 새 결과 파일을 저장하므로 원본을 덮어쓰지 않습니다. 변환 실패·출력 20MB 초과에는 오류를 표시하고 원본을 보존합니다. 대량 프레임·초고해상도 이미지에는 서버 메모리 보호 한도가 적용됩니다.

기존 저장소의 원본 PNG/JPG는 그대로 보관하며, 배포 시 `scripts/optimize-images.cjs`에서 WebP와 작은 카드용 이미지를 만듭니다. 이미지 설명·본문·DB 원본 주소는 유지하고 공개 HTML에서 최적화 파일을 선택합니다. 이전 `/images/*.png` 주소는 해당 WebP로 연결됩니다. 파일 내용의 해시를 주소에 넣어 장기 캐시를 사용해도 수정된 이미지는 새 주소로 표시합니다. 임의의 사용자 이미지 URL이나 SVG를 이 변환기로 재작성하지 않습니다.

공개 목록·상세는 한 번의 Supabase RPC로 필요한 데이터를 함께 읽습니다. 반복 요청에서는 DB의 공개 변경 번호를 매번 확인한 후 최대 30초 동안 서버 메모리 캐시를 재사용합니다. 글 수정·발행·예약 자동 발행·비공개 전환·삭제·카테고리 변경은 같은 DB 트랜잭션에서 변경 번호를 갱신해 다음 요청이 새 데이터를 읽게 합니다. DB 확인에 실패하면 캐시를 반환하지 않습니다. 관리자·브라우저·CDN의 페이지 응답은 여전히 no-store로 유지합니다. 공개 조회수/인기 순위는 최대 30초 동안 이전 값이 보일 수 있고 실제 집계 및 관리자 통계는 계속 DB를 사용합니다.

## 관리자와 카테고리 사용

비밀번호는 관리자 상단의 ‘비밀번호 변경’에서 현재 비밀번호를 확인한 뒤 직접 바꿀 수 있습니다. 비밀번호를 GitHub·환경변수·채팅에 넣지 않습니다.

추가 관리자는 Supabase Authentication에서 사용자가 직접 계정을 생성한 뒤, 해당 계정에 `admin_users` 행을 등록합니다. 아래는 **예시값**이며 SQL Editor에서 실제 이메일과 원하는 아이디로 바꿉니다. 아이디는 영문 소문자/숫자/밑줄 3~40자입니다. 일반 Auth 사용자에게 관리자 권한을 자동으로 부여하지 않습니다.

```sql
insert into public.admin_users(user_id,role,username)
select id,'admin','another_admin'
from auth.users where email='admin@example.invalid';
```

‘카테고리 관리’에서 새 분류, 이름·영문 주소·순서·활성 상태를 관리합니다. 분류 ID와 기존 글은 유지됩니다. 비활성 분류의 글은 공개 목록/상세/사이트맵/인기 순위에서 숨겨집니다. 해당 글을 수정·저장하려면 활성 분류로 옮기거나 분류를 다시 활성화합니다.

## 조회 통계와 보안

조회수는 상세 화면이 보일 때 서버에 기록합니다. Netlify의 연결 IP와 브라우저 정보를 HMAC으로 처리하며 원래 IP/브라우저 정보를 DB로 보내지 않습니다. 같은 식별 정보의 30분 내 새로고침/반복 열람은 증가하지 않습니다. 같은 네트워크에서 같은 브라우저 정보를 사용하는 방문자는 함께 집계될 수 있습니다. 관리자 세션 쿠키가 있는 요청과 알려진 봇은 제외합니다.

누적 카운터·조회 기록·한국 시간의 일별 합계는 한 트랜잭션에서 처리합니다. 최근 7일/30일은 오늘을 포함한 한국 시간 날짜 범위입니다. 일반 방문자는 카운터나 조회 기록을 직접 수정할 수 없습니다. 조회용 Edge 함수는 전용 서버 비밀값을 검증하고, 관리자 작업은 Auth 사용자 확인·DB 관리자 역할·RLS를 함께 검증합니다.

Free 플랜에 맞춰 일별 합계를 보관합니다. 조회 기록이 많이 쌓이면 35일이 지난 중복 확인 기록만 SQL Editor에서 정리할 수 있습니다. 일별 합계와 누적 카운터는 유지됩니다. 자동 삭제 작업은 등록하지 않았습니다.

```sql
delete from public.post_views where viewed_at < now()-interval '35 days';
```

보안 Advisor에서 DB/RLS 관련 경고는 없습니다. 유출 비밀번호 검사 알림은 [Supabase Pro 이상 기능](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)이므로 이번 Free 구성에서는 활성화하지 않았습니다.

## 정식 운영으로 전환할 때

현재 Deploy Preview는 Netlify 팀 로그인으로 보호됩니다. 테스트 중 이 보호를 끄지 않았습니다. 기본 주소에 CMS를 적용해도 정식 발행 전 개발 데이터 구분과 noindex 설정은 유지합니다. 기본 주소의 `/login`에서 같은 관리자 아이디로 로그인하며, 프리뷰 주소의 로그인 쿠키는 다른 주소로 이전하지 않습니다. 정식 운영 설정은 사용자의 발행 결정 후 적용합니다.

- 운영 도메인을 서버의 `SITE_URL`로 설정합니다. SEO canonical과 사이트맵은 이 값을 사용합니다.
- 운영 배포의 `CMS_ENVIRONMENT`를 production으로 설정하고, Deploy Preview는 preview로 유지합니다. Netlify 비밀값 검사와 충돌하지 않도록 이 설정은 환경 이름을 담은 구조화된 값도 지원합니다.
- 현재 조회수 비밀값은 사용자 승인 후 **기본 배포와 Deploy Preview**에 등록합니다. 두 주소는 같은 preview DB 검증 해시를 사용합니다. 정식 운영용 `CMS_VIEW_SECRET`은 별도로 생성하고 production 해시를 `cms_private.view_bridge`에 등록합니다. 서버 전용 비밀값과 Supabase 전체 DB 접근 키를 공개 코드에 넣지 않습니다.
- 운영에 필요한 글만 명시적으로 production에 복사합니다. preview 자료와 테스트 조회 기록을 일괄 이전하지 않습니다. 두 원본 글은 `content/legacy-posts.backup.json`으로 보관돼 있습니다. 테스트 자동 발행/운영 데이터 복사 기능은 실행하지 않았습니다.
- CMS 코드는 main에 반영하고, 운영 데이터 전환은 별도 설정으로 진행합니다. 발행 화면의 글 저장/수정에는 이후 Git 커밋이나 Netlify 재배포가 필요하지 않습니다.

카테고리/관리자까지 개발·운영을 물리적으로 분리하려면 별도 Supabase 프로젝트를 사용하고 배포 맥락별 연결 값을 지정합니다. 현재는 기존 프로젝트 한 개를 사용하는 구조이며, 유료 브랜치나 새로운 유료 서비스는 추가하지 않았습니다.

## 검증 기록

단계별 수정 파일과 검사 결과는 [CMS_PROGRESS.md](CMS_PROGRESS.md)에 기록했습니다. 원본 브라우저 데이터, 정적 글 소스와 백업은 보존했습니다. 테스트 게시글·조회 기록·일별 테스트 합계는 정리했고, 시험 분류는 비활성으로 보관했습니다. 20MB 한도 검증에 사용한 이미지도 비공개로 보존합니다.
